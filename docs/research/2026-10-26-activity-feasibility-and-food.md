# Activity feasibility and requested food rankings

**Date:** 2026-10-26. **Question:** Which requested statistics can this server-only connector collect honestly, what remains conditional, and what would “most food ate” / “most common food eaten” require?
**Current disposition: hard crossplay server-only; implementation PAUSED.** The [authoritative plan](../superpowers/plans/2026-10-26-server-only-discord-leaderboards.md) now includes optional simulation-dependent rack/oven completions alongside participation/damage and independent activity boards. MistrCech is an optional **server installation**; players need no mod or handshake. Exact food-eaten/popularity remain **excluded**; no client mod/custom messages or eat-animation replacement. Companion passages below are historical alternatives, not current options or approval questions. This consistency revision uses already-audited evidence, not repeated research.

## Findings in plain terms

* **Possible server-only, with honest labels:** sampled moving-helm seconds; conservative **inferred** floor-pickup quantities; new Piece placements with **estimated standard recipe materials**. These are implementable observation contracts, not completed/live-verified features. Pickup inference still has residual misclassification risk.
* **Creator representation is no longer an open design problem:** the inspected game already joins platform identities into a typed current player list. Use that list, history index and unique character/socket/profile corroboration; do not invent Steam/PlayFab normalization. This conclusion is static, not proof of the installed runtime.
* **Exploration is conditional:** sampled observed footprint is feasible only with active runtime grid parameters. Private client minimap history is a different metric. Headless grid availability is unresolved; constructor defaults/static assets and biome lookups do not resolve it.
* **Optional rack/oven completions are proposed:** accepted inserter provenance plus a durable slot generation can credit validated completed output units once. This is not eating, insertion-attempt or retrieval counting; source findings and the bounded contract are below. Simulation presence alone does not establish station ownership or complete coverage.
* **Exact requested food rankings are excluded server-only:** reliable remote-client food units/prefabs were not established by reviewed signals. Server-visible eat animations are real, but not reliable food transactions; historical client-attested alternatives are outside the hard constraint, not pending approval.
* **Not everything client-owned is invisible:** forwarded requests can be observed. A request, current status or animation does not by itself establish a completed action, inventory debit, quantity, payer or period timestamp.

These conclusions distinguish static capability from observed coverage. No app code, tests, builds, game/mod execution, deployment or production access was performed for this note.

## Creator bridge: resolved statically through game-generated identities

The previously open **representation/normalization** question is closed for B1. No hostname prefix table, key migration or change to existing combat/account identity rules is needed.

1. `Piece.SetCreator(long, PlatformUserID)` writes profile creator and `ZDOVars.s_creatorIndex`. Bounds-check that index against current `ZNet.World.m_playerHistory`; its entry is `ZNet.CrossNetworkUserInfo`, with `m_id: PlatformUserID`.
2. `ZNet.GetPlayerList()` returns `List<ZNet.PlayerInfo>`. `PlayerInfo` has `m_characterID: ZDOID` and `m_userInfo: CrossNetworkUserInfo`; use `m_userInfo.m_id`, not name, playfab string or a fabricated field.
3. Require history/current IDs `.IsValid` **before equality**, then enumerate all current entries and require exactly one match. `Splatform.PlatformUserID.Equals` may equate two invalid IDs; invalid==invalid must never attribute a creator.
4. Resolve the matched nonzero `m_characterID` through the existing unique ready/connected socket resolver. Require its current character ZDO `s_playerID` to equal the piece's profile creator, with no duplicate/conflicting profile/character/account mapping. Stable stored identity remains `peer.m_socket.GetHostName()`.
5. Recheck current world/connection/session at acceptance; clear cached player/profile/history mappings on world changes. A stale player-list snapshot, disconnect, missing history, invalid/duplicate ID or mismatched character rejects the candidate; delayed availability may be reconsidered only within the existing candidate window.

Why the typed join works (B2): `ZNet.UpdatePlayerList` creates Steamworks IDs with `new PlatformUserID(m_steamPlatform, peer.m_socket.GetHostName())`, PlayFab IDs with `new PlatformUserID(peer.m_socket.GetHostName())`; unsupported backend gets `PlatformUserID.None`. `ZSteamSocket.GetHostName()` is Steam ID text; `ZPlayFabSocket.GetHostName()` returns `m_platformPlayerId.ToString()`, **not** remote entity ID. Reuse the game's generated typed list instead of rebuilding that conversion yourself.
`ZNet.TryGetPlayerByPlatformUserID` returns a first match: useful implementation evidence, **not uniqueness proof**. Never substitute it for enumerating duplicates.
Remaining checks are actual runtime compatibility/freshness/unique mappings and useful coverage, not an unresolved string-normalization design. Two same-name accounts remain distinct. Retain these guards in the existing resolver/activity flow; the authoritative plan owns proportionate tests, not a new API/task or exhaustive fake-game suite.

### What the ordinary local action really does (B2)

`Humanoid.UseItem(Inventory,ItemData,bool)` resolves the actual inventory and checks membership. An `Interactable.UseItem` can handle it and return before consumption; a generic use-item postfix is therefore not a food event.
For ordinary consumables, successful `ConsumeItem` leads to consume effects, `m_zanim.SetTrigger("eat")` and temporary use-hand item visuals. `Player.ConsumeItem` checks `CanConsumeItem`, applies status effect, calls `EatFood` only when `m_food > 0`, removes one inventory item and returns true. **It ignores `EatFood`'s return.** `ConsumeItem == true` alone is not a reliable food-action success witness under changed/nested/modded behavior.
`Player.EatFood(ItemData)` validates `CanEat`, then adds/replaces a food entry or refreshes an eligible existing one. `Food.CanEatAgain()` is `m_time < m_foodBurnTime / 2`; too-early repeats fail. Successful branches increment `PlayerStatType.FoodEaten` and per-food profile statistics. A food action can change a slot/timer rather than increase food-list length.
An action-grade local adapter must correlate the same item/prefab, successful food-list action, **one actual item decrement** and successful completed enclosing invocation; avoid nested duplicate callbacks and exceptional/failed originals. Neither blindly patching `UseItem`, `ConsumeItem` return nor `EatFood` alone establishes the complete action. Alternate interactable/placed-food sources require an explicit equivalent-debit/coverage contract before claiming they are included.
`Player` saves/loads food names/times as local player data; profile counters are local historical statistics, not replicated collector events. They lack our observation/world/session/event boundaries and cannot prove when/where this collector saw a unit consumed. A profile counter increment is a useful local hook clue, not a server-side report ledger.

### What the server can see — and why that is insufficient

`ZSyncAnimation.SetTrigger("eat")` sends `InvokeRPC(Everybody,"SetTrigger",name)`; `RPC_SetTrigger` applies an animator trigger. That is visible animation traffic, not an assertion that the server sees nothing. The normal consumable path can generate it after success, **including ordinary potions**; interactable/placed consumables and mods can trigger it too (B2).
`Humanoid.SetUseHandVisual` calls `VisEquipment.SetRightItemVisual`; the owner writes `ZDOVars.s_rightItem` / `s_rightItemQuality`. This temporary visual may identify a probable item, but it travels separately from the animation. Coalescing, loss/order, fast restore and repeated same-hash use can defeat one-to-one correlation. Gear/health changes are also not inventory receipts/debits.
Consequently, counting “eat” animations cannot reliably answer either requested ranking; guessing prefab from nearby visual state does not repair it. An independently approved metric named **eat animations observed** could count something else, but it is not the requested food statistic and is **not proposed as a silent replacement**. Unknown prefab/action must not be guessed into a “most common food” board.
ValheimPlus's pinned `EatFood` duration patch shows a local seam, not replication (V1). MistrCech's reviewed source supplies no verified food-sync adapter (M1). Dashboard mock foods/crafting and Jotunn custom networking do not add an action witness (D1/J1).

### Historical companion alternative — excluded, not an approval question

This historical feasibility list explains the difference between a consumption action and animation telemetry. **It is outside the current plan and must not be implemented**: the user requires no client mod/custom client messages. A hypothetical client-attested source would not be cheat-proof or independently server-verified inventory accounting.

* Client captures a completed eligible food action and one debit, canonical prefab and quantity; no food-list load/timer or animation-only events. Define alternate consumable/interactable coverage explicitly and expose excluded paths.
* Server derives actor from authenticated current connection/character mapping and derives current session/world; do not trust submitted account, name or world. Validate item against a compatible canonical prefab catalog and reject unknown/malformed food classifications.
* Use per-session event sequence with durable world/session/account/sequence dedup before incrementing totals. Define restart/reconnect/replay/gap behavior and missing/unsupported client coverage; no blind acceptance of re-uploaded historical counters.
* Bound payload size, numeric quantities, rate and pending memory before writes. A separate contract must choose exact limits, version/compatibility rules and acceptance/ack behavior; no new RPC endpoint or dependency is authorized here.
* Use **server receipt UTC** for report attribution unless a separately approved clock protocol exists; never accept arbitrary client backdating. Delayed/offline/missing events therefore affect period coverage and must be labeled, not silently replayed into past reports.
* Keep existing calendar/claims, local UTC mapping, durable dedup and literal no-mentions rendering if integration is later approved; design how extra rows fit the existing budget before adding them. Disclose “client-attested / partial participating-client coverage,” including residual falsification/loss risk.
