## Current: longest bow hit (November 7)

New default-off **`[Server-Observed Activities] Longest Bow Hit Enabled`** adds **🏹 The Hawk of Huginn — longest bow hit**, metric identity **26**. It reuses the optional Dedicated Simulation `Character.ApplyDamage` observation: the actual victim must be a valid server-owned untamed creature, the attacker must resolve to a current known player, the original handler must succeed and observed HP must actually decrease. **Without the mod or for client-owned victims, nothing is recorded; there is no fallback or equipped-weapon/projectile-name proxy.** All existing collectors and Norse section titles remain.

**Native feasibility was checked in the real compile-reference IL.** `Attack.FireProjectileBurst` copies the weapon's `m_skillType` into `HitData.m_skill` and calls `SetAttacker`. `Projectile.Setup` retains that skill, and `Projectile.OnHit` restores it plus the projectile owner into the impact `HitData` before `IDestructible.Damage`. `HitData.Serialize/Deserialize` carry the skill and attacker ZDOID across `RPC_Damage` into `ApplyDamage`. `Skills.SkillType.Bows` is **8**; Crossbows **14**, ElementalMagic **9** and BloodMagic **10** are distinct and excluded. The inspected vanilla path preserves bow classification through arrow impact; this is reference-assembly evidence, not live execution or a guarantee that custom weapons label skills correctly.

Distance is **3D between the victim's server-owned ZDO position and the attacker's latest accepted ZDO position at hit observation**, not arrow travel, muzzle-to-impact or launch distance. The attacker endpoint must still match its accepted owner/data revision and be **0–2.5 monotonic seconds old**, inclusively. This is a non-consuming read of the existing bounded freshness cache: a sampler may already have consumed the endpoint, and several hits may reuse it while fresh. Invalid/nonfinite endpoints, unknown attackers, stale/future/missing/ownership- or revision-mismatched positions and distances **over 250 m** count zero. The inclusive 250 m cap allows headroom above roughly 200 m normal bow range without accepting arbitrary position jumps. Attacker movement and replication delay can change this observed distance; no client launch position is inferred.

Each valid hit persists a bounded immutable activity observation through the existing worker and durable token deduplication. Daily and weekly queries take each account's **maximum**, never the sum or last hit, inside the usual half-open UTC period. No new map, unbounded leaderboard cache, database collection or value-embedded LiteDB predicate is added. The flag controls capture and report inclusion independently of damage/kill flags. Reports retain all **19 sections**, numeric ranks and the existing adaptive name reservation under **1,900 UTF-16 units**; no second message or dropped section is introduced. Current Release harnesses pass **480 checks**: 66 Statistics, 40 Tracking, 60 Reporting, 15 Startup and 299 NativeAdapters. Worst weekly/preview cases use **1,867/1,848 UTF-16 units**; longest-biome-label cases use 1,852/1,862. Build/checksum evidence is recorded in the testing bundle provenance. These checks do not verify live Valheim/Harmony/NPS/crossplay/Discord behavior.

### Player biome source

The existing two-second authenticated player-ZDO sampler queries `WorldGenerator.instance.GetBiome(x, z)` only for fresh, finite current-player positions. It works without an initialized minimap or creature ownership. The generator must be non-null, and None/unknown biome values count zero. ### Boss-key source and repeat kills

[BossDefeatPatches](../DiscordConnector/Patches/BossDefeatPatches.cs) observes the server's `ZoneSystem.RPC_SetGlobalKey(long sender, string name)` after a successful original handler. The enclosing native receive must provide the actual authenticated `ZRpc`, matching ready peer/claimed sender and a server-addressed None-ZDO `SetGlobalKey` envelope. Missing/local-only provenance, skipped/failed handlers, enclosing receive failures, stale connections/worlds and disabled capture count zero. The existing bounded signal admission/exception barriers are reused; the new decoded sibling is included in native-hook inventory so The Berserker and other signals keep their existing capability checks.

Only `defeated_eikthyr`, `defeated_gdking`, `defeated_bonemass`, `defeated_dragon`, `defeated_goblinking`, `defeated_queen` and `defeated_fader` qualify. This is an exact allowlist, not a prefix match: `defeated_serpent`, nonboss and unknown keys are excluded. The seven names are corroborated by the [documented global keys](https://valheim.fandom.com/wiki/Global_Keys); serialized prefab assets were not inspected.

The sender needs a fresh position; it and other currently resolved players within **50 m in 3D**, inclusively, receive one credit. Positions come from the same two-second sampler, have a **2.5-second** age limit in both clocks and must still match the account/connection/current character. No boss position, hit participation or last hit is inferred. One cohort shares one durable token. Duplicate signals for the same world/boss key within **60 seconds** are suppressed regardless of sender; the serialized worker also enforces the recent-key window across restart. Distinct bosses and repeat events at the 60-second boundary can count. Legitimate same-boss kills faster than this are intentionally coalesced.

**Repeat kills do reach the handler in the referenced game code.** `Character.OnDeath` calls `SetGlobalKey(m_defeatSetGlobalKey)` for a nonempty defeat key; `SetGlobalKey(string)` always routes to the server. The existing-key short-circuit is inside `RPC_SetGlobalKey`, not the owning client's send path. The hook observes a successful handler invocation even when that handler returns because the key already exists. No workaround, key reset or fake death event was added. This remains an authenticated client-originated signal: admin key commands or malicious clients can produce credits without a genuine boss death, and the sending owner is not necessarily the killer.

## Current source: admission, diagnostics and lifecycle

- [Admission](../DiscordConnector/Records/ObservationAdmission.cs) allows **128** newly completed signal replay identities per authenticated account **and** connection over rolling **60 seconds**. Raw activity has a separate **128/seven-second** allowance. Genuine server-local work has its own allowance, not a fabricated peer. Each policy retains at most **128 remote account/connection pairs**, bounded account/connection indexes and **16,512 charges** (128×128 +128 local). Reconnects do not erase unexpired charges; temporary world unavailability preserves tombstones. These limits can reject legitimate bursts and do not stop distributed flooding or prove gameplay truth.
- Separate replay caches remain manual **256/seven seconds**, signals **4,096/60 seconds**, raw activity **4,096/seven seconds**. At most **32** expired entries are examined per admission; expiry is strictly older than the window. Shared scope depth/pending observations are **16**; staged signals older than **five monotonic seconds** are rejected. Unrelated/disabled nested RPCs mask parent provenance without consuming observation replay/quota or copying parameter payloads. Exact supported schema and authenticated transport remain prerequisites.
- [Worker admission](../DiscordConnector/Records/ActivityStore.cs) reserves **16 outstanding signal batches/64 KiB** per account and per connection, including executing work; local work has a separate identical allowance. Indexes retain at most **128 remote origins**. Reservations release on completion/failure, not reconnect. One serialized worker retains the global **256-batch**, **128 physical-document/batch**, **8 MiB** signal-charge and **two report-job** bounds. Gameplay uses at most **255** outstanding batches; one existing slot is reserved for one diagnostic reconciliation job. This is bounded accounting, not another queue/worker.
- [Loss accounting](../DiscordConnector/Records/ObservationLoss.cs) separates confirmed rejected **metric-captures** from uncertain writes. Duplicate suppression is not a new loss. A failed gameplay batch may already have committed some rows: uncertainty conservatively counts affected captures, including possible duplicates/commits, not absent events or failed operations. Nothing replays gameplay, callbacks, report claims or Discord sends.
- Only immutable **absolute diagnostic snapshots** may reconcile. Additive `server_observation_v2_loss` documents are keyed by world/metric/process epoch; per-field monotonic maxima make repeated/lower/lost-ack snapshots idempotent. One acknowledgment may be pending, normal submissions are at least **ten monotonic seconds** apart, and memory retains at most **64 world/metric keys**, without eviction/reset to mint capacity. Saturation, a 65th key or exhausted diagnostic dedup marks incompleteness with a bounded redacted warning. Dirty newer values survive older acknowledgments. Stored `KnownLosses`/`Rejections`/`UncertainWrites` are **world-lifetime totals, not report-period losses**. Summed report diagnostics are metric-captures, not unique network/game events; uncertain captures may be stored. Missing/unreconciled state and abrupt exit remain incomplete.
- [Native capability](../DiscordConnector/Patches/NativeSignalPatches.cs) inventories exact targets, own hook identities/kinds/priorities/order and supported foreign owners only at the **first usable session and session/world changes**, not each frame. Capture is unavailable until inspection succeeds. A session includes current world UID, ZNet/World/ZDOMan object identities and server UID; even a same-UID replacement world invalidates staging. Unsupported replacements fail unavailable; arbitrary mid-session hot-patching is unsupported. Configuration invalidates cached capture options; unchanged coverage is polled at most once/second except transitions/flushes.
- [Plugin lifecycle](../DiscordConnector/Plugin.cs) isolates world/observation, coverage, loss maintenance, manual polling and automatic polling/ticks. One failing stage does not disable unrelated scheduling; invalid calendar configuration may still disable that scheduler. Exception-safe shutdown contains each cleanup, attempts one final diagnostic submission, then seals admission/starts the owned background drain in `finally`, even after an earlier cleanup failure. Database closure waits for admitted work/readers; Unity never synchronously waits. Status reports pending work, known failures, dirty diagnostics and incompleteness. **Drained is not all writes succeeded; a Task does not keep the process alive.** Stuck work can retain the handle, and forced/process exit can lose queued/unflushed observations or unreconciled totals. There is no verified host async-stop durability guarantee.

It observes the existing zero-payload `RPC_HitWhileDodging`, not a new client message. The authenticated simulation/reporting connection, unique current beneficiary character/account and actual addressed ZDO owner are validated separately; the owner may be a distinct authenticated ready peer or server. Missing live local view/ownership is unavailable, never guessed. Dispatch rechecks world/session/full character, transport and owner.

Visibility is partial: same-client simulation-to-dodger dispatch is invisible to the server. One dodge can emit **multiple notifications**; envelope dedup suppresses repeated observer stages/retransmissions, not distinct attacks/dodges. This is **not a perfect-dodge statistic, proof of accepted rewards, unique attacks or complete dodges**. Handler throttling/reward acceptance is not witnessed. Positive stored history remains visible under its own inclusion flag even when capture is currently unavailable. Native evidence/NPS source pins remain in the [approved design](superpowers/specs/2026-11-02-observation-pipeline-redesign-design.md); adapter checks are not native runtime execution.

Passing isolated checks and a real game-reference build do **not** prove live Valheim/Harmony/mod/Discord behavior. The previous build delivered manual previews on November 1; that does not validate the new lightweight capture paths or all rollout steps below.
